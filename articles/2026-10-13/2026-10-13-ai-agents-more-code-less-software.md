# AI 写代码更快了，但软件没有变多：一项 700 家公司研究揭示的"审查瓶颈"

> 原帖：[AI coding agents generate more code, but not more software](https://arstechnica.com/ai/2026/10/ai-coding-agents-generate-more-code-but-not-more-software/)（Ars Technica，HN 297 分 / 254 评论）
> 研究来源：Harvard 大学 Fiona Chen 与 James Stratton，基于 Jellyfish 工程分析平台数据

## 一句话结论

AI coding agent 确实让代码写得更多了——但公司层面的软件产出没有显著变化，因为效率增益被下游的人工 code review 瓶颈整个吸收掉了。瓶颈没有消失，只是从"写"转移到了"审"。

## 研究是什么

这项研究由 Harvard 的 Fiona Chen 和 James Stratton 完成，数据来自工程分析平台 Jellyfish，覆盖 700 多家软件开发公司、超过 70 万名员工、3 亿条工作事件（commit、PR 等），时间跨度从 2021 年到 2026 年 3 月。

方法上，研究者通过 AI 使用量的直接测量和 GitHub 活动分析，确定每家公司引入 AI 编码助手和 AI agent 的时间点，然后用差分法（difference of differences）回归比较引入前后的关键指标变化。这不是问卷或自述研究，而是真实工程活动的观测数据——这是它值得认真对待的原因。

## 核心发现：代码多了，软件没多

引入 AI agent 后，公司的代码生产端出现明显增长：

- **代码总行数 +30%**
- **commit 数量 +20%**
- **Pull Request 数量 +23%**

但代表真实软件产出的指标纹丝不动：Jira 等工具追踪的 Issue 和 Epic（即完整软件功能）的解决率在统计上没有显著变化，这些任务的规模和复杂度分布也没有发生" compositional shift"。

多出来的代码去哪了？答案在审查环节：

- **PR 从提交到合并的平均审查时间 +49%**
- **要求修改的 PR 占比几乎翻倍**
- **每个 PR 的评论数 +35%**
- **参与 code review 的员工占比 +14%**

同时，研究者交叉比对 Jellyfish 活跃员工数和 LinkedIn 数据后，**没有发现 AI 对雇佣人数的显著影响**。

## 机制：瓶颈转移，而非瓶颈消失

这项研究最有价值的不是某单个数字，而是它揭示的结构：**软件开发的总吞吐量不由最快的环节决定，而由最慢的环节决定。**

AI agent 把"写代码"这个环节的成本打到近乎于零，于是整个流水线的约束条件转移到了"验证代码"上。而验证恰恰是 AI 目前帮不上太多忙的环节：截至 2026 年 3 月，80% 的受测公司已经使用了某种形式的 AI code review，但 AI agent 只贡献了 23.3% 的审查评论和 10.8% 的 PR——绝大部分审查工作仍然由人类完成，而且做得更累了。

换句话说：写代码的速度提高了，但信任代码的速度没有。

## 社区在吵什么

HN 讨论区（254 条评论）的分歧集中在"该怪谁"上。

**一派认为问题在审查文化，不在 AI。** 高赞评论指出，资深工程师"无论 agent 进步多少，都很难放弃逐行审查"。如果写代码的成本下降 100 倍，组织理应学会跳过一些流程——但这种变化不会首先发生在成熟工程团队，而是会出现在采用"无人审查"激进实践初创公司。

**另一派反怼：审查压力本来就是技术债。** 有人说得更直白——如果那段后端代码真的关键到"300ms 延迟值几百万"，为什么没有测试和基准？因为"超级程序员 Greg"把所有知识都存在自己脑子里，好当变更的最终裁判。"这在 agentic coding 之前就是毒瘤，现在依然如此。写文档，加测试。"

**还有一条技术路线的佐证很有意思**：一位开发者让 LLM 审计自己的测试套件，结果 10 万行测试里约 6 万行被判为"接近无用"——mock 得太狠，实际什么都没测。这暗示审查瓶颈的部分解法，可能恰恰是用 AI 清理 AI 时代之前留下的劣质测试。

## 边界与不确定性

这篇研究有几个必须标注的边界：

1. **数据截止 2026 年 3 月**。此后模型有明显升级，"审查瓶颈"的严重程度可能已经缓解，也可能随着 agent 使用深度增加而进一步恶化——现有数据无法回答。
2. **Issue/Epic 解决率是滞后指标**。代码产出增加后，功能交付可能需要更长时间才能体现。差分法是观测性研究，不是随机实验，因果强度有限。
3. **Jellyfish 指标可能低估 agent 的隐性价值**。快速原型、技术验证（spike）、探索性脚本这类不进 PR 的工作，不会出现在这套指标里。一位评论者说得对：AI 真正的高价值场景之一就是"快速搭一个触碰大量架构决策的原型，然后扔掉"——这部分收益研究测不到。
4. **Ars 的措辞值得注意**：研究原文说的是"little evidence that firms increase software output"，即"没有证据表明产出增加"，这与"证明产出没增加"是两回事。

## 我们该关注什么

对正在大量使用 coding agent 的团队，这项研究指向三个可操作的问题：

1. **你的度量指标挂在哪里？** 如果考核的是代码行数和 commit 数，agent 会让数字很好看；如果考核的是交付功能数，结论可能完全不同。
2. **审查产能有没有跟着扩？** PR 需要"changes requested"的比例近乎翻倍，意味着团队的实际验证负担在加重。不扩审查产能，写代码的提速就是纸面的。
3. **信任机制能否产品化？** 社区讨论里反复出现的方向是：把人类关注点持续固化成规则、测试和基准，让机器可检查的部分交给机器，人类审查留给真正高影响的变更。这本质上是把 code review 从"手工艺"变成"工程"。

Fred Brooks 几十年前就说过要"计划扔掉第一个版本"。AI agent 没有推翻这个判断，只是把"哪个环节最贵"重新洗了一次牌。
