# 如何用 agent.md 解决 LLM 辅助编程的代码质量问题

**来源**：[Hacker News - My agent.md to improve LLM-assisted code quality](https://fabiensanglard.net/agent.md/index.html)
**作者**：Fabien Sanglard
**HN 评分**：129 分
**发布时间**：2026年8月21日

---

## 核心观点

Fabien Sanglard 分享了一个简单但有效的实践：通过在项目根目录创建 `agent.md` 文件，并将其注入到 LLM 的 prompt 中，显著提升了 LLM 生成代码的质量。这不是什么黑科技，而是将重复的代码审查提示固化成了一个可复用的配置文件。

## 问题的演进

Sanglard 的经历很有代表性：

**2025年中**：第一次尝试 LLM 辅助编程，用于 Rust 的 mDNS 实现 `libadbmdns`。结果代码甚至无法编译。

**2026年1月**：再次尝试，这次效果好多了。LLM 不仅写出了复杂的索引二叉堆类，还发现了一个 Windows IOCP 实现中的 bug（在 `polling` crate 中）。

**但问题依然存在**：代码质量极差。像意大利面一样纠缠，没有注释，没有结构。如果速度优势被后续的代码清理抵消，那 LLM 辅助就失去了意义。

**2026年3月**：开始使用 Antigravity 和 VS Code 的 Claude Code 插件这类 agentic IDE。可以"迭代"暂存代码了。但发现自己像个老师，不停地对"无限耐心的初级计算机专业学生"说同样的话："不要用魔法数字"、"在这里加个简短注释"、"用短函数名"。

代码质量确实提升了，接近手动编写的水平。但太累 —— 每次新会话都要重复同样的建议。

## 解决方案：agent.md

当编码会话开始时，编码工具会加载项目根目录下的 `agent.md` 文件并将其注入到 prompt 中。这是**微调编码风格偏好的完美位置**。当 Sanglard发现自己重复给出同样的代码改进建议时，就把它们加到这个文件里。

Sanglard 的 `agent.md` 包含的具体规则：

1. **简洁性**：给人看的文字（注释、commit message、回复）要尽可能简短，每个词都要精心挑选
2. **避免过度赞美**：不要说"你绝对正确"，直接给事实
3. **避免魔法数字**：将重复或有意义的值提取为常量或枚举；一次性、自解释的值保留在行内
4. **减少缩进**：避免 Arrow Anti-Pattern，利用 early return 和 continue
5. **短函数名**：不超过 30 个字符
6. **用枚举替代布尔参数**
7. **呼吸感**：逻辑块之间加空行
8. **注释原则**：简短说明"做什么"和"为什么"，必要时用 ASCII 图示
9. **访问控制**：将成员可见性变更视为破坏性设计变更，除非设计明确要求，否则保持私有
10. **分层抽象**：底层机制（硬件 I/O、扇区解析、原始 socket 流）必须封装在专门的驱动/抽象层中
11. **最小变更**：不要碰与所实现功能无关的代码块
12. **严格分层**：每层只能与紧邻的下层通信，不能"穿透"层级
13. **大括号**：即使单行 if 也要用大括号
14. **Commit 规范**：遵循 7 条明确的 commit message 规则
15. **TDD 原则**：修 bug 时先写测试，观察失败，再写修复，观察通过

## 有效性分析

Sanglard 强调这个"技巧"**显著改善了生成的代码质量**，但**不是万能药**。LLM 仍然会幻觉，不能被信任。他仍然需要大量验证和迭代，但现在可以专注于架构和设计，而不是代码风格。

这里的关键洞察是：**将人工审查中的重复模式自动化**。这不是在教 LLM 如何写更好的代码逻辑，而是在教它如何写出更符合特定团队/个人风格的代码。逻辑质量仍需开发者把守，但风格和规范的执行成本被大幅降低了。

## Context Dilution 问题

Sanglard 提到了一个 LLM 的已知问题：**context dilution**（上下文稀释）或 **attention dilution**（注意力稀释）。这来自论文 [Lost in the Middle](https://arxiv.org/abs/2307.03172)。

随着上下文增长，模型开始较少关注中间的指令，而更关注开头和结尾的内容。原因尚不明确。Sanglard 找到两种缓解方法：

1. **保持上下文简短**：每个功能启动新会话
2. **显式要求重新加载 agent.md**：当看到代码质量下降时，说"Reload agent.md"就够了

这是一个重要的实践提示。`agent.md` 不是设置一次就完事的配置，而可能需要根据上下文状态主动刷新。

## 自动更新机制

一个巧妙的细节是：Sanglard 不需要每次打开编辑器来添加新规则。他直接让 agent 更新 `agent.md`。

这意味着整个系统是**自举的**——当他在审查代码时发现新的需要改进的模式，可以直接告诉 LLM "把这个规则加到 agent.md 里"。这形成了一个正反馈循环：代码审查 → 发现模式 → 更新 agent.md → 未来代码自动遵守。

## 评估与启示

这篇文章的价值在于它的**实用主义**：

1. **不追求完美**：Sanglard 清楚地知道 LLM 的局限性，不指望它生成完美的代码。他的目标是"足够好的代码风格"，将精力节省下来专注于架构和设计。

2. **利用现有机制**：`agent.md` 不是新发明，而是对现有工具（agentic IDEs 会自动加载）的创造性使用。很多工具已经支持类似的配置注入机制，只是没有文档化或被广泛认知。

3. **显式化隐性知识**：优秀的代码审查者会在脑海中有一套"好代码"的标准，但这些标准往往是隐性的。`agent.md` 将这些标准显式化、可复用化。

4. **分层治理**：通过 agent.md 管理"代码风格和规范"，通过人工审查管理"架构和逻辑"。这是一个合理的责任分工。

## 可复制性

这个实践的可复制性很高，但需要注意：

- **工具依赖**：需要使用支持自动加载 `agent.md` 或类似文件的工具。如果工具不支持，可能需要手动复制粘贴或编写脚本。
- **团队适配**：Sanglard 的规则反映了他个人的编码偏好。团队使用时需要集体讨论、达成共识。
- **维护成本**：`agent.md` 本身需要维护和更新。但随着时间的推移，这个成本应该下降，因为常见模式会被逐步覆盖。

## 结论

Sanglard 的实践提供了一个简单但深刻的启示：**在 LLM 辅助编程中，明确的规范和约束比更强大的模型更重要**。

通过 `agent.md` 将编码风格偏好显式化、自动化，开发者可以将精力从"纠正代码风格"转移到"验证架构逻辑"。这种分工不仅提升了效率，也让 LLM 的输出更可预测、更易审查。

这不是要取代代码审查，而是要让代码审查变得更有价值 —— 专注于真正重要的事情，而不是反复纠正同样的问题。
