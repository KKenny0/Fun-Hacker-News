# agent.md：用一份配置文件拯救 LLM 生成的代码质量

> Fabien Sanglard 分享了他如何通过 `agent.md` 文件将 LLM 生成的代码从"意大利面条"提升到接近生产级别的质量。

---

## 从失望到突破：一个开发者的 LLM 辅助编程之路

Fabien Sanglard 的 LLM 辅助编程经历并非一帆风顺。2025 年中，他首次尝试用 LLM 加速 Rust 项目 `libadbmdns` 的开发，结果令人失望——生成的代码甚至无法编译。

到了 2026 年 1 月，情况有所改善。LLM 不仅帮他写出了复杂的索引二叉堆类，还发现了 `polling` crate 中一个与 Windows IOCP 实现相关的晦涩 bug。但新的问题出现了：代码质量极其糟糕。

"那是意大利面条式代码，没有注释，没有结构，" Fabien 写道。虽然 LLM 加快了开发速度，但清理代码到生产级别的时间成本完全抵消了效率提升。

## 重复的审查过程催生 agent.md

2026 年 3 月，Fabien 开始使用 Antigravity 和 VS Code 的 Claude Code 插件等 agentic IDEs。这让他能够对"暂存"的代码进行迭代。他发现自己像在审查一个"无限耐心的计算机专业大三学生"，不断给出同样的反馈：

- "不要使用魔法数字"
- "在这里加个简短注释解释一下"
- "使用简短的函数名"

代码质量确实显著提升，甚至接近他手写的水平。但这个过程变得极其繁琐——每个新会话都要重复同样的指导。

**这就是 `agent.md` 登场的时刻。**

## agent.md：代码风格的个人宪法

Fabien 发现，许多 agentic coding harness 会在编程会话开始时加载一个名为 `agent.md` 的文件，并将其注入到 prompt 中。这成为了他精确调优代码风格偏好的完美位置。

"当我发现自己为了提升代码质量而重复给出同样的建议时，我就把它加到那里，" Fabien 解释道。

他分享了自己的 `agent.md` 内容，作为一个起点：

### 核心原则

**1. 极简主义表达**
- 给人类看的内容（注释、提交消息、prompt 回复）用最少的字
- 每个字都要精心挑选，将体量压缩到绝对最小
- 直击要害，少即是多

**2. 拒绝奉承**
- 避免最高级和赞美
- 不要告诉我"你完全正确"
- 给我冷酷的真相

### 代码质量规则

**3. 消除魔法值**
- 将重复或有意义的值提取为描述性常量（const）或枚举
- 保持自解释的一次性值内联，避免杂乱
- 如果值来自规范（如 HTTP 200 OK），无论如何都使用常量

**4. 减少缩进**
- 避免 Arrow Anti-Pattern
- 利用 early return 和 continue

**5. 命名规范**
- 函数名保持简短，少于 30 个字符
- 用枚举替代布尔参数

**6. 可读性**
- 让代码读者有呼吸感，在逻辑块之间添加空行
- 添加简短、切中要害的注释，解释"做什么"和"为什么"
- 尽可能使用例子，提出 ASCII 图来解释完整系统

**7. 访问控制**
- 将成员可见性变更视为破坏性设计变更
- 除非外部访问是设计严格要求的，否则所有字段和函数保持私有
- 在将任何访问修饰符从 private 改为 internal 或 public 之前，明确提示用户批准

**8. 抽象层次**
- 按抽象层次编程
- 低级机制（如原始硬件 I/O、扇区解析、直接 socket 流）必须封装在专用驱动/抽象层中
- 向应用程序的其余部分暴露干净的高级 API，使调用代码使用领域概念，而不是原始实现细节

**9. 最小化变更**
- 不要触及与你实现的功能无关的代码块
- 例如，如果你没有创建或修改某个代码块，就不要给它添加注释
- 尽可能最小化实现功能时更改的行数

**10. 分层边界**
- 严格遵守分层边界层次：每层只能与其正下方的一层直接通信
- 永远不要"穿透"层级（例如，控制器或 UI 组件绝不能直接调用数据库查询、原始硬件驱动或低级网络客户端；始终通过中间服务/抽象层路由）

**11. 代码风格**
- 即使是单行 "if" 语句，也要始终使用 {}

### 提交消息规范

Fabien 还制定了 7 条提交消息规则：

1. 用空行分隔主题行和正文
2. 主题行限制在 50 个字符（72 是绝对硬限制）
3. 主题行首字母大写
4. 主题行不以句号结尾
5. 主题行使用祈使语气（如"修复 bug"、"添加功能"，而不是"已修复"或"添加"）
6. 正文手动换行到 72 个字符，以防止 Git 格式问题
7. 使用正文解释"什么"和"为什么" vs "如何"。假设代码解释了"如何"；消息必须解释上下文和推理

### TDD 原则

- 如果 prompt 指示正在修复 bug，不要立即编写修复
- 首先编写测试，观察它失败
- 然后编写修复，观察测试通过

## 不是银弹，但值得尝试

"虽然这个'技巧'大大改善了生成的代码，但这并不是让我避免阅读代码的灵丹妙药，" Fabien 警告道。"LLM 会不断产生幻觉，不能被信任。我仍然必须验证和大量迭代，但现在我通常专注于架构和设计，而不是代码风格。"

## 应对上下文稀释

Fabien 还提到了一个令人烦恼的 LLM 现象：**上下文稀释（context dilution）** 或 **注意力稀释（attention dilution）**，这在《Lost in the Middle》论文中有概述。

随着上下文增长，模型开始减少对上下文中间部分的指令的注意力，而更多地关注开头和结尾。他找到了两种最小化影响的方法：

1. **保持上下文简短**：这意味着为每个功能启动新会话
2. **明确要求重新加载 agent.md**：当看到代码质量下降时，说"Reload agent.md"就足够了

## 自动更新 agent.md

你不需要每次想添加新规则时都打开编辑器。Fabien 现在的做法是直接让 agent 更新 `agent.md`。

## 价值评估

这篇文章的价值在于：

1. **实践导向**：不是理论讨论，而是来自真实开发一线的经验总结
2. **具体可操作**：提供的规则可以直接应用，无需复杂配置
3. **承认局限**：不夸大 LLM 的能力，明确指出仍需人工审查和迭代
4. **关注细节**：从命名规范到分层架构，覆盖了代码质量的多个维度

对于正在使用或计划使用 LLM 辅助编程的开发者来说，`agent.md` 提供了一种系统化的方法来提升生成代码的质量。它将零散的代码审查反馈凝聚成一份可复用的配置文件，让开发者能够专注于更高层次的架构和设计决策，而不是重复的代码风格纠正。

正如 Fabien 所说，这不是银弹，但它确实让 LLM 辅助编程从一个"好玩的玩具"变成了一个更实用的工具。
