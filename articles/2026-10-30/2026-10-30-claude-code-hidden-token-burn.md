# Claude Code 的隐藏"状态栏税"：15-20% 的 token 花在三个词上

> Hacker News 2026-10-30 榜单 · 558 分 / 224 评论
> 原文：<https://gist.github.com/flamerix-ai/c3905705cc4205e5de3011fa2e74efce> · 讨论：<https://news.ycombinator.com/item?id=50284255>

## 一、异常：一个"副业查询"花掉了比主对话更多的钱

Flamerix AI 团队在 Claude Code 的 OpenTelemetry 导出数据里发现异常：按 `query_source` 分组统计后，一个叫 `agent_summary` 的查询类型，**周花费占比 16.4%——比主对话本身（15.7%）还高**，占全部 API 请求的近五分之一。输入输出Token比高达约 9000:1，其中 96% 的开销落在 Opus 上。

这个查询在干什么？答案荒诞得近乎行为艺术：**每隔约 30 秒，Claude Code 会把每个后台 agent 的完整对话记录发给它自己的模型（通常是 Opus），只为让模型生成 3-5 个词，用于更新 agents 面板里那行状态描述。** 这些词永远不会进入你的对话上下文，纯粹是给人类看的 UI 装饰。

更麻烦的是，这个行为自 2026 年 8 月的 2.1.232 版本起默认开启，且**没有任何官方开关能关掉它**。作者还联合了 HN 上的其他独立测量者——GitHub issue #86879 收录了四份 18-26% 区间的独立测量，互相印证。

## 二、为什么关不掉：一个被"堵死"的配置空间

Gist 里"为什么没有设置项"一节堪称逆向工程范本：

- **文档里的开关只管开、不管关。** SDK 选项 `agentProgressSummaries` 默认值明明是 `false`，但打包后的代码里它只是一个 OR 表达式的一个分支，所有代码路径都写入 `true`；
- **间隔由服务端控制。** 它来自按模型家族下发的服务端 flag，钳制在 30-240 秒，默认已是下限，没有任何值能禁用计时器；
- **显而易见的环境变量全部落空。** 一些发行版会设置的 `DISABLE_NON_ESSENTIAL_MODEL_CALLS` 在二进制里根本不存在；`CLAUDE_CODE_FORK_SUBAGENT=0` 等变量确实有效，但代价是把整个 fork 子代理或后台 agent 功能一起杀掉；
- **成本工具看不见它。** 这些请求不写入本地会话日志（issue #104358），官方文档的 token 说明也没提它——唯一能观测的通道就是 OpenTelemetry 导出。

最有讽刺意味的是：2.1.310 其实已经内置了更省的 `short` 模式（用约 2k token 的笔记代替完整 transcript，还可指定更小的模型来写）——**但默认关闭，且只有服务端 flag 才能切换**。作者的时间线梳理显示，这个功能 2 月首次出现在代码里，8 月默认开启，10 月间隔变为服务端可调——一路只增不减。

## 三、修复：70 行代码的 Bun preload

作者的方案 `no-agent-summary.js` 很精巧：由于 Claude Code 以预编译 Bun 字节码发布，改 JS 文本无效，API 客户端也不走可包装的 `fetch`。但 `Function.prototype.toString` 对字节码里的回调依然返回源码——于是这个 hook 只包装全局 `setTimeout`，用回调源码中的日志锚点（如 `[AgentSummary] Timer fired`）识别摘要计时器，返回一个延迟为 2³¹−1 毫秒的惰性句柄（再大会被 Bun 当成 1ms 立即触发）。通过 `BUN_OPTIONS=--preload=...` 注入，不修改任何二进制。实测从 2.1.257 到 2.1.312 各版本，`off` 模式下摘要请求全部归零，其他功能无恙。

## 四、HN 评论区：缓存命中救得了钱包吗？

评论区最大的争论点是：transcript 反复重发，绝大部分走 prompt cache，是不是其实"很便宜"？反对方算了一笔账：即便缓存读按 0.1 倍计价，一个 800k token 的子代理 transcript 每 30 秒被重读一次，十次就烧掉了相当于整个会话冷预填的成本；Gist 作者也承认，约 2% 的冷缓存请求承载了超过三分之一的成本。**对订阅用户而言，损失的不是账单，而是限流额度**——16% 的配额花在状态栏上，等于你的主力工作时段凭空缩水五分之一。也有人顺带吐槽这类"隐形功能"正是 harness 臃肿化的缩影。

## 五、值得记一笔的三件事

第一，**可观测性是唯一的防线**。这个成本能被揪出来，靠的不是账单（订阅制下根本没有明细），而是团队自己接了 OpenTelemetry。在 agent 工具链日益黑盒化的今天，"钱花到哪去了"这个问题，答案往往只在你自己搭的遥测管道里。

第二，**"fail-open"的工程自觉值得学习**。作者明确说明：某次 Claude Code 更新可能改掉锚点字符串、让 hook 静默失效，所以每次升级后都要跑验证脚本确认计时器确实被抑制。给系统打补丁不难，难的是诚实地告诉用户补丁何时会失效。

第三，对普通用户的建议很实际：重度使用后台 agent 的话，装上这个 preload 或至少关闭 agents 面板；轻度用户影响有限，但值得知道自己每一单位配额里，有几分钱在为三个词的"演出"买单。工具厂商把高成本功能默认打开、把关闭选项留在服务端——这个先例本身，比 16% 这个数字更值得警惕。
